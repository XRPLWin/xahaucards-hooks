Scope & method

Four hooks across two accounts, at the pin above. Shop account: shop.c (payment gate), doors.c (grant / allowance admin). Issuer account: mint.c (roll + mint), manager.c (admin + attestor signatures). Shared: namespaces.h, trigger.h. The source read is hook/src/ — the tree that builds hook/build/*.wasm.

This is a review, not a formal proof: each rule reads as holds, fails with a stated input, or out of reach of a static read. The rules checked are your own (the whitepaper's invariants and the 61 checks in hook/live-test.mjs). The state contract and trigger/callback were read in full; each hook was read against its rules; an adversarial pass then tried to break every "holds"; the protocol facts the findings depend on were checked against xahaud source and live Xahau testnet state; the draft was put through an internal red-team and a protocol/calibration panel. Questions for you to settle

Not defects — places where only you can say which reading is authoritative.

Question  Q1 — Edition numbering is keyed per full card code, not per subject

mint.c:831/837 key the edition counter by the whole 17-byte code (CODE_LEN = 17), i.e. XC-<theme>-<subject>-<rarity>-<attack>-<health>, including the rolled stats. Confirmed in source and in live state (on-chain edition keys read e.g. XC-01-061-C-03-04). So the same subject rolled with different stats, or at a different rarity, gets independent edition sequences each starting at #1. We read the whitepaper's numbering as "per subject"; the code keys per full card code. If we've read the whitepaper right, those are two different scarcity models, and the number is sealed into immutable metadata at mint. Which is authoritative is yours to state; if per-subject is intended, the key length at :831/837 would need to cover the subject only.

Question  Q2 — A non-XAH (IOU) payment to the shop is accepted, not bounced

shop.c:191-192: a payment whose sfAmount is not native is accepted (tesSUCCESS), documented as "not XAH, passing… received, not bounced". It records no purchase, so the "records no purchase" rule holds. The only open question is whether receiving an IOU here (rather than rejecting it) is intended. Your call.

Low-severity findings

None lets an outside party steal funds, mint a pack, or sign as someone else — self-inflicted, confined to a trusted role, or a recoverable residual. Reported for completeness and hardening.

Low  L1 — A failed delivery Remit leaves the buyer with nothing and no on-ledger claim

The lifecycle promises "paid → cards, or a recorded claim" (shop.c:80-86). There is a window where neither holds. The mint applies at L+1 and emits five Remits (the cards) for L+2; the callback keys off the mint's result, which is tesSUCCESS (it emitted fine), so it deletes the intent record (trigger.h). The five Remits resolve at L+2 with no callback watching. If any Remit fails at L+2, the intent is already gone — the buyer paid, got nothing, and there is no record that anything is owed.

The clearest trigger: a buyer who passes the receivability check at purchase (shop.c:338-349) then sets lsfDisallowIncomingRemit before L+2; mint.c does not re-check (no flag reference in the file), and a Remit to such an account fails tecNO_PERMISSION (xahaud Remit.cpp:294-296) atomically — no token is minted anywhere. That case is self-inflicted (only the account owner can set the flag; no attacker profit), which anchors it at low. But two parts are structural: the callback comment (trigger.h:316-318) wrongly calls this "a card minted to the issuer… card in hand" — for any atomic Remit tec no card is minted at all; and the record is deleted before delivery is confirmed, so any L+2 Remit tec leaves a paid buyer with no claim. Recommend: correct the comment, ensure recovery tooling does not treat "no FAILED record" as proof of delivery, and (to close it outright) re-check the buyer's flags in mint.c before minting.

Low  L2 — Card annotation depends on emitted-transaction apply order (measured to hold; not source-guaranteed)

Per card, mint.c emits the metadata SetRemarks before the Remit that mints the token (:1160-1183 then :1187-1222), and a SetRemarks on a not-yet-existent token fails tecNO_TARGET, which is final. So a card's metadata depends on the mint applying first.

Measured — holds across the full deployment

On the testnet issuer, the entire transaction history shows 73 metadata SetRemarks, all tesSUCCESS, and 70 mint Remits, all tesSUCCESS — zero tecNO_TARGET (and account_tx includes failed tec transactions, so this is not a "only complete cards are visible" artifact). Directly: in 25 of 25 paired cases the mint Remit applies at a lower in-ledger index than its SetRemarks. No card has ever landed un-annotated.

But we could not establish the ordering as a protocol guarantee from source — the rule that orders same-account, sequence-0 emitted transactions within a ledger is not one we could pin down (a naive read predicts intermittent failure, which the evidence contradicts, so emitted transactions are ordered by a rule we did not locate). It holds in practice; we cannot prove it must. Recommend cheap insurance rather than reliance: issuer-side tooling that detects any minted URIToken lacking its meta remarks and re-emits the SetRemarks — recoverable, because those remarks are not sealed until written — or a confirmation of the emitted-ordering rule from the xahaud maintainers.

Low  L3 — An enrolled attestor can pre-sign any card and repoint its art

attest() lets any roll member sign any card this issuer minted (manager.c:553). A card takes one signature, first-writer-wins (:719-726), and signing seals meta.1's image URL to the signer's slot (:924-956). A malicious or careless roll member could pre-sign cards to block the intended signer and repoint the art, spending their own SIGS allowance. Bounded by that allowance, requires roll membership (semi-trusted by design), cannot move funds, mint, or sign as another attestor. A design tradeoff, not an authorization break.

Low  L4 — Same-ledger duplicate signature over-spends the signer's own allowance

The duplicate-signature scan (manager.c:648-726) reads the card's current on-ledger remarks, so two Invokes for the same card in the same ledger both pass it, both decrement the allowance (:742-745), and the second's SetRemarks fails tecIMMUTABLE a ledger later. Net: that slot's own allowance drops by two for one signature. Self-harm only, consistent with the documented spend-before-emit stance (:730-741). Your call whether it warrants a guard.

Per-hook — what holds

Holds  shop.c — payment gate

One state write only — state_set(intent, txid) at :409, own namespace, accept path, after every validation check, before the emit; no write on any reject path (a refused purchase records nothing, strongly). Exact price both directions (:240); partial-payment rejected with a correct sign-guard (:181-183); THEME exactly two bytes (:255); set-exists (:276) and on-sale (:304); buyer receivability checked (:338-349); budget-below-price guard (:369). Intent keyed by the unique Payment txid. Note: THEME digit-ness is enforced only by the table lookup — holds because only cards:export writes those keys.

Holds  doors.c — grant + allowance admin

GRANT gated on sender == issuer KEY_CLAIM (:153-160), fail-closed if unset; ALLOW gated on sender == the shop account itself (:352-359), capped at GRANTS_MAX. The two use different sender checks, so the always-online claim key can spend the allowance but cannot raise it — a compromised claim authority is bounded to allowance × ≤10 XAH. Writes only the shop's own namespace; the removed WITHDRAW door leaves no dangling reads.

Holds  mint.c — roll + mint

  • Seed / no buyer grind. seed = sha512half(parent_txid ‖ ledger_last_hash()) (:643-648); ledger_last_hash() is the hash of the ledger the buyer's Payment landed in (xahaud HookAPI.cpp), and the trigger provably executes at L+1, so the reveal hash post-dates the buyer's signature. No reroll path (the callback does not re-emit).
  • Independently re-derived from public data (free cross-check). We reproduced a real minted pack end to end from public inputs alone — buyer payment 712EEBCF…, ledger_last_hash EAF06F0F…, and the on-chain shape record — and the five re-derived card codes match the five actually minted on-chain (identical as a set; only the mint order differs). So the roll is a pure, reproducible function of chain data with no operator input — verified from outside the code. Runnable script included.
  • Disclosed residual (in your source): the five-ledger emit window lets whoever includes the trigger pick among ≤5 candidate hashes. Legendary is 2/256 per card, so ~3.85% chance of ≥1 legendary in a five-card pack, which a proposer choosing among five candidate seeds (and willing to burn packs) could lift to ~17.8%. Only a block proposer, only by burning packs, never the buyer — strictly weaker than the payer-grind the design closes.
  • Rarity strip / stat bands. :724-725 partitions 0..255 into 150/70/26/8/2 exactly; :369-370 give contiguous non-overlapping stat bands, membership enforced by construction, legendary pinned 20/20.
  • Five new tokens to the buyer (buyer from the intent record, not the trigger sender). Metadata / seal flags corroborated on the inspected card XC-01-026-C-04-04: meta.0 immutable, meta.1 mutable, meta.2 immutable, schema immutable.
  • Notes: table-sourced strings are copied into card JSON without escaping (:944, :973-977) — relies on the admin door / loader to reject "/\; every sellable set must populate all five rarities or a share of packs fail-closed (:737).

Holds  manager.c — admin + attestor signatures

Admin gated on hook_account == sender (:125-126) — the issuer only; this is the KEY_CLAIM write-guard doors.c depends on. Signing requires an issuer-written roll entry keyed by the sender (:574-579) — no self-enrol. The signature allowance is fail-closed on absent/malformed and decremented only after every check, before the emit (:611-617, :742-745). The junk-URIToken sign attack is closed (URI_MIN_LEN + scheme/offset checks + issuer==hook, :894-905, :632-645). The full signature lifecycle is corroborated on real cards: an unsigned card carries meta.1 mutable; a signed card (XC-01-366-R-10-12) carries CardSignature immutable, meta.1 now immutable (sealed by signing), and is owned by a buyer, not the issuer.

Composition — the four hooks together

Namespaces are separated by design; shop.c/doors.c write only NS_INTENT, mint.c only NS_EDITIONS, manager.c only issuer namespaces on its own account; no hook writes another's across an account (foreign writes need an sfHookGrants entry — confirmed against xahaud — and none is granted but manager's own-account write). By design the four do not co-fire on one transaction. The one shared record (the intent) is keyed by the unique txid, so one purchase's record cannot touch another's. No clobber path was found.

Adversarial pass — attacked and not broken

  • Forge an emission to mint a free pack — blocked in the transactor (source read): a transaction carrying sfEmitDetails without the node's internal emitted flag is rejected (telNON_LOCAL_EMITTED_TXN, Transactor.cpp:127-148), the network refuses emitted transactions off the wire, and an emitted transaction's sender must equal the emitting hook's own account (HookAPI.cpp rule 0). The issuer's gate (sender == KEY_SHOP and sfEmitDetails) only accepts a genuine emission from the shop's own hooks.
  • Underpay / IOU / partial-payment — blocked at shop.c. Grant forgery / over-drain — blocked (claim-key check, allowance floor and ceiling, no counter wrap, 10-XAH cap). Sign without being an attestor / sign a non-card — blocked. Admin action by a non-issuer — blocked. Clobber another hook's state / forge an intent to claim a refund — blocked. Roll grinding by a buyer, double-mint of one payment, edition collision, cheap griefing — all hold.
Assumptions accepted, not re-verified — part of this review
  • The emission-forgery bar is a read of the xahaud transactor, not a transaction we submitted. It is the linchpin of "no free pack".
  • The callback's delivery decision reads the trigger's engine result (sfTransactionResult, trigger.h); the source comment says this was measured on testnet — we did not re-run it.
  • Edition-collision freedom relies on per-transaction hook-state commit within a ledger (standard Xahau behaviour, and what mint.c:812-821 designs around); accepted, not independently re-run.
Out of scope for this tier / to confirm on the deploy side
  • Deployment bindings (not in the source): each hook's installed HookNamespace must equal its NS_* constant; the HookCanEmit grants; the ISSUER parameter and the SHOP/CLAIM settings. Worth a checklist against deploy.mjs.
  • The installed wasm bytes. This review reads the source that builds them; it does not prove the deployed hook/build/*.wasm is that source. Matching the published build hash to the deployed HookHash closes that gap — the proof tier does this against the bytes.
  • The loader's input validation — several mint-side safeties (JSON-breaking characters, table record widths) are backstops that assume the admin door / loader rejects bad input on the way in.
